## Context

当前 `/api/dashboard/summary` 返回最近完成的 `SUCCESS`/`FAILED` 子任务，Dashboard 直接逐行展示 `recent_completed_tasks`。任务历史页已经有批次列表、批次统计、整体状态计算和批次详情入口；实现应复用这些既有语义，避免 Dashboard 自己重新定义批次状态。

## Goals / Non-Goals

**Goals:**

- 为 Dashboard 提供完整批次级近期完成摘要。
- 保持单次任务和运行中任务的现有展示与跳转行为。
- 让显示数量按 Dashboard 可见条目计算，批次不因子任务多而被拆散。
- 保留进入现有批次详情和结果文件入口的能力。

**Non-Goals:**

- 不修改远端执行、任务状态流转、报告生成或批次数据存储。
- 不把运行中任务改成批次聚合视图。
- 不在 Dashboard 展开全部子任务或复制历史页完整详情布局。

## Decisions

### 1. 后端按完整批次聚合

在 Dashboard summary 中新增独立的 `recent_completed_batches`，按批次维度返回摘要；单次任务继续由 `recent_completed_tasks` 返回。批次查询必须先确定最近完成的批次，再加载该批次全部子任务计算统计，不能从已限制的子任务结果在前端反推。

备选方案是仅在前端对现有 50 条子任务分组，优点是改动小，但批次会因接口 limit 或状态筛选而缺少子任务，整体结论不可靠，因此不采用。

### 2. 复用现有最终状态语义

批次聚合沿用任务历史已有的最终状态和报告级失败判断，至少返回整体 `status`、成功数、失败数、取消数、活动/等待数、总数、服务器数、创建/结束时间和耗时。这样可以覆盖“执行成功但报告失败”的情况，避免 Dashboard 与历史页口径分裂。

### 3. 前端使用混合条目模型

Dashboard 将近期完成数据转换为统一的展示条目：`kind=batch` 显示批次摘要，`kind=single` 显示单次任务。批次行使用现有表格和状态组件，提供“查看批次详情”操作；单次行保持现有任务跳转。显示数量在转换后的条目上截取。

### 4. 接口兼容与降级

新增字段采用可选前端类型。旧后端未返回批次摘要时，前端继续显示已有单次任务列表，不阻塞 Dashboard；批次摘要加载失败时保留单次完成任务并给出轻量提示，不影响运行中任务。

## Risks / Trade-offs

- [批次聚合查询增加数据库读取] → 只对有限数量的最近批次聚合，并复用已有索引/批次查询；先测量响应时间，避免恢复项目空间递归扫描类的 Dashboard 超时。
- [历史页与 Dashboard 状态规则漂移] → 抽取或复用现有批次状态计算边界，并增加同一 fixture 的 API/前端回归测试。
- [批次行信息多导致窄屏拥挤] → 保持摘要字段紧凑，次要统计使用辅助文本，操作按钮使用明确短文案并在窄屏下允许换行。
- [旧 API 与新前端并行发布] → 前端对 `recent_completed_batches` 缺失做兼容回退，发布顺序不要求先升级后端。

## Migration Plan

1. 增加批次摘要响应结构和后端聚合查询。
2. 增加 API、批次状态和前端混合条目测试。
3. 完成前端构建后按现有部署脚本发布。
4. 若出现问题，回滚前端静态资源和后端代码；任务记录与远端执行不受影响。
