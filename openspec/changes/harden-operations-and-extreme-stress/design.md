## Context

现有平台是单实例 FastAPI + SQLite 控制器：SSH 连接由 Paramiko 建立，远端任务和恢复监控由进程内线程执行；任务模型已有 `worker_id`、租约和远端 PID/报告恢复机制。服务器记录支持 `key` 与 `password` 两种认证，首次连接当前自动接受 SSH 主机密钥。极限压测已是一个原子远端任务，CPU/内存与 GPU 同步启动并保留 15% 内存。

完整发布脚本为保护活动任务而拒绝重启后端，但其同时构建和覆盖前端静态文件。任务产物、SQLite 数据库和滚动备份均位于控制器本机；已有按天清理与目录占用统计，但没有基于分区余量的准入阈值。

## Goals / Non-Goals

**Goals:**

- 保持密码首次接入和公钥部署流程，同时使每次远端操作可验证目标 SSH 身份。
- 将极限压测的“可否运行、是否冲突、异常后远端是否已停止”变成明确、可审计的状态。
- 在不引入外部队列或云服务的前提下，补足当前单实例的任务资源互斥、容量可见性和前端热发布能力。
- 让历史结果能以同服务器、同类任务为范围提供可解释的退化提示。

**Non-Goals:**

- 不取消密码认证、不强制将历史服务器立即切换为密钥认证，也不修改远端账户密码。
- 不在本变更引入 Celery、Redis、分布式调度、多实例后端或对象存储。
- 不承诺跨不同型号硬件、不同压测参数或不同软件版本的性能横向比较。
- 不把“远端不可达”误判为远端任务已停止。

## Decisions

### 1. 采用“显式信任（TOFU）+ 指纹变更阻断”，而非静默接受

首次连接只读取并返回 SSH host key 指纹；操作员确认后才将 fingerprint、算法和确认时间保存到服务器记录。已保存指纹的连接使用拒绝未知/不匹配指纹的策略。需要换机、重装或轮换 SSH host key 时，操作员在服务器详情页比较旧/新指纹后显式更新；更新动作写入审计日志。

密码登录继续可用于首次探测与公钥部署。公钥部署完成后，平台用该服务器选定私钥做一次独立连接验证；成功时提供“改用密钥认证”和“清除已保存密码”两个分离、确认式动作。清除仅置空控制器数据库中的密码，不删除远端 `authorized_keys`。

替代方案是由控制器维护全局 `known_hosts` 文件或强制人工在服务器上执行 `ssh-keyscan`。前者不利于逐服务器审计和 UI 确认，后者会让首次接入流程脱离平台；因此采用服务器记录中的已确认指纹。实现应复用相同校验逻辑于探测、执行器和公钥部署，防止入口不一致。

### 2. 极限任务采用“预检快照 + 服务端最终校验”

前端在选择服务器后请求只读预检，用于即时展示；提交 API 必须再次执行决定性校验，防止浏览器数据过期或绕过 UI。预检结果按 `pass`、`warning`、`blocked` 归类，保存为任务参数/事件证据；仅 blocked 项拒绝创建，warning 项（例如依赖可自动准备）由操作员看到后允许继续。

检查项包括：SSH 身份已确认且可连通、GPU/NVIDIA 可用、依赖状态及可自动安装性、可用内存与 15% 保留要求、监控可用性、远端/控制器存储余量及资源冲突。温度读取缺失作为 warning，不因监控工具缺失误阻断已有可运行的压测；实际温度保护仅在有可信采样时启用。

替代方案是把所有检查留在远端脚本启动时完成。该方案不能阻止无效任务进入历史，也不能在 UI 中解释风险，故不用。

### 3. 资源互斥先按“服务器 + 资源域”落在数据库事务中

定义任务资源域：极限压测占用 `gpu`、`cpu_mem`；GPU 压测占用 `gpu`；CPU/内存压测占用 `cpu_mem`；磁盘压测和只读监控不进入该互斥集合。创建任务时查询该服务器所有未终态任务的资源域，在同一数据库事务中拒绝交集。返回冲突任务 ID、名称和状态，并记录审计原因。

为避免两个并发请求同时通过检查，SQLite 写入阶段使用事务中的重新校验；实现可配合一个短生命周期的服务器级进程锁，但数据库记录是最终依据。任务进入终态、恢复、重试和取消时统一以状态重新计算，不依赖仅存在内存的锁。

替代方案是为所有任务设置“每服务器仅一个活动任务”。它会阻断安全的巡检与磁盘任务，且不符合资源域互斥的目的，故不用。

### 4. 异常处置使用“证据优先”的终态说明

为极限压测增加连续采样阈值和连接失败阈值配置。超温触发时请求停止两个模块并验证远端 PID/结果清单；取消亦走同一整体停止流程。若 SSH 已失联，任务不能声明远端已停止：保存最后心跳、最后远端 PID/报告证据、已尝试的处置与建议人工命令，并显示为远端状态未确认的受关注结果。

这沿用现有“后端重启只恢复监控、不重启远端压力”的原则。替代方案是连接失败即标记 FAILED/CANCELED；该方案会丢失远端可能仍在运行的安全事实，故不用。

### 5. 历史基线是确定性、保守的同机比较

完成任务提取稳定可得的摘要指标（结果、温度峰值、错误/UE/ECC、性能或持续时长）。新结果只查询同一 `server_id`、同一压力类别、相同或兼容参数签名的最近 SUCCESS 基线。没有基线时标识“首个基线”；数据缺失则不作退化判断。阈值来自受控系统设置，结果展示比较值与基线任务 ID，避免黑盒评分。

替代方案是全局排名或跨机器平均值；硬件差异会使其误导运维判断，故不采用。

### 6. 容量告警使用控制器数据分区余量和两级阈值

以数据库、产物和备份所在分区的 `disk_usage` 为权威，按目录计算产物/备份占用作为解释数据。设置 warning 与 blocking 两个阈值：warning 仅显示告警，blocking 拒绝会产生大量证据的极限压测；已运行任务不受影响。自动清理状态沿用现有设置和审计记录，仪表盘将同时展示上次结果与当前余量。

替代方案是仅按产物目录大小触发清理；它无法识别数据库、备份或同分区其他服务耗尽空间，故不用。

### 7. 前端独立发布构建到版本目录并原子切换

新增受限的前端发布脚本：安装/锁定依赖并构建到临时版本目录，检查产物与 `nginx -t`，随后原子切换 Nginx `root` 指向的发布目录（例如通过受控 `current` 符号链接或目录 rename）。该路径不调用后端 `systemctl restart`，不运行活动任务拦截；失败时删除未激活版本并保留当前版本。完整发布脚本仍保持活动任务保护。

替代方案是直接 `cp` 覆盖 `/var/www`。覆盖期间可能产生混合版本资源，且缺少回滚目标，故不用。

## Risks / Trade-offs

- [历史服务器没有已确认指纹，启用后首次操作需确认] → 仅将其标为“待确认”，提供受控批量只读采集和逐台确认，不静默写入信任值。
- [服务器重装或 SSH host key 轮换会阻断任务] → 显示旧/新指纹、原因和确认更新入口；写审计日志。
- [预检与提交间状态变化] → 提交 API 再次校验，前端预检只作体验展示。
- [温度工具读数不可靠或缺失] → 采样来源和有效性随证据保存；缺失时预警而非伪造温度保护。
- [SQLite 并发互斥存在短暂锁竞争] → 使用短事务、明确冲突响应，并覆盖并发提交测试；后续规模化时再迁移调度架构。
- [前端原子发布依赖部署目录权限与 Nginx 配置] → 仅由现有受控部署用户执行，发布前校验并保留上一个静态版本以回滚。

## Migration Plan

1. 先发布数据模型与只读 SSH 指纹采集/展示，现有服务器维持可用但标为待确认；验证不改变任务执行。
2. 发布服务器确认、密钥验证与可选密码清除；对新建服务器默认要求确认指纹后才允许远端变更。
3. 发布极限压测预检、后端互斥和异常证据，使用单服务器与恢复/取消回归测试验证后逐步启用阻断阈值。
4. 发布容量状态、基线显示和前端独立发布脚本；在有活动任务时演练一次前端发布与回滚。

回滚时：关闭新预检/容量阻断开关即可恢复提交路径；保留已采集指纹和证据不影响旧记录；前端发布通过切回上一静态版本回滚；完整部署始终保留现有活动任务拒绝重启规则。

## Open Questions

- 温度预警和阻断的默认阈值需按 GPU 型号或服务器标签配置，实施前以现有测试机采样结果确定；这不改变“持续超温才触发整体处置”的行为契约。
