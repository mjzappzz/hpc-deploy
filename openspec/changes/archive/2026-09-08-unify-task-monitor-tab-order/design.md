## Context

当前三个任务观察入口分别定义监控标签：任务执行页与批次详情使用静态 `el-tab-pane` 声明，普通历史详情使用计算属性生成的标签数组。三个定义已发生排序漂移。变更动机见 `proposal.md`。

## Goals / Non-Goals

**Goals:**

- 使运行中 stress 任务在三个入口使用相同、可预测的标签顺序。
- 在不改变标签可见性、数据获取、默认面板和终态行为的前提下，将 GPU 置于 CPU 与磁盘之前。

**Non-Goals:**

- 不抽取跨组件共享的标签配置。
- 不调整监控 API、采样频率、实时日志或非 stress 任务的标签集合。

## Decisions

- 在现有定义处直接调整呈现顺序，而不引入共享配置。该变更只涉及稳定的静态顺序，抽取会扩大改动面；直接调整保留每个入口现有的任务类型和终态条件。
- 采用“执行日志、GPU、CPU 与内存、磁盘”作为统一顺序。GPU 压测的首要观测信息靠前，且用户已确认需要所有入口一致。
- 统一可见的中文标签为“CPU与内存”和“磁盘 I/O”。任务执行页原有“CPU/内存”“磁盘”与历史详情不一致；仅修改文案与排序，不修改面板名称和监控类型。

备选方案是在各组件间复用单个标签配置。由于三处的摘要、终态、任务类型条件不同，当前抽取会耦合这些条件且超出本次排序修复范围。

## Risks / Trade-offs

- [静态模板和计算数组仍分散维护，未来可能再次漂移] → 以针对三个入口顺序的前端测试覆盖本次契约；若未来标签类型或条件扩展，再评估抽取共享配置。
- [标签变窄/变宽影响小屏布局] → 使用现有 Element Plus 标签布局，并在构建后进行浏览器尺寸验证。

## Migration Plan

1. 添加能覆盖三个入口排序的测试，并先确认其在现状失败。
2. 调整两个视图中的标签顺序和任务执行页文案。
3. 运行前端测试、类型检查/构建和浏览器验证。
4. 回滚时仅恢复两个视图中本次标签声明的顺序与文案；不涉及数据迁移或服务重启。
