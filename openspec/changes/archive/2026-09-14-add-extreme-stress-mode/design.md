## Context

现有压测套件会将 GPU、CPU/内存和磁盘作为独立任务按固定顺序运行；单独并发两个既有任务无法保证实际负载同时开始，且取消、恢复和历史状态会被拆散。相关目标见 `proposal.md`。

## Goals / Non-Goals

**Goals:**

- 以一个远端编排进程完成依赖准备、ready 协调、同步启动、双向停止和证据汇总。
- 不改变既有常规压测和磁盘并发策略。
- 让首次直接运行极限模式仍能自动安装依赖，而已完成常规压测的服务器可复用已有依赖和缓存。

**Non-Goals:**

- 不在极限模式中运行磁盘 I/O 压测。
- 不将 GPU 或 CPU/内存子模块暴露为可独立取消、重试或历史成功的任务。
- 不改变 GPU 显存压力策略或常规模式的内存安全策略。

## Decisions

### 单一编排任务而非两个并发平台任务

新增极限编排脚本作为平台唯一远端任务，并在其工作目录中管理 GPU 与 CPU/内存子脚本、子进程 PID 和报告。平台只需管理一个 PID 文件、状态、取消和恢复入口；总报告可稳定引用同一任务目录下的子证据。

替代方案是创建同一批次的两个并发平台任务。该方案无法保证共同屏障，取消与恢复会分裂，且用户已确认极限压测不可拆分，故不采用。

### 准备阶段串行，负载阶段同步

编排器先受控完成 GPU 与 CPU/内存依赖安装、包管理和可能的 `gpu-burn` 构建，再启动两个模块进入 ready。这样首次运行仍可自动准备，同时避免 `dnf`/`apt` 锁、编译 CPU 争抢和一个模块负载已启动而另一个仍安装依赖。两个模块仅在共享 start barrier 释放后启动实际 `gpu-burn` 与 `stress-ng` 负载。

子脚本将获得受控的 prepare/ready/start 接口，正常独立运行路径保持兼容；编排器记录单调时间和墙钟时间并校验实际启动偏差不超过 2 秒。

### 统一终止与更严格的内存保护

编排器维护两个模块的进程组标识。任一预检失败会阻止屏障释放；任一运行失败、同步偏差超限、超时、内存保护触发或外部取消都会先终止仍在运行的一侧，再收集已有证据。极限模式向 CPU/内存子脚本传递至少 15% 物理内存的保留线，覆盖 GPU 驱动、CUDA pinned memory 和监控的额外主机内存消耗。

### 结果模型与历史展示

编排器输出机器可解析的总结果，包含 GPU、CPU/内存和同步校验的状态、起止时间、时长、偏差和首个失败原因。报告解析以总结果决定该任务的最终 PASS/FAIL；同时收集子模块的 TXT/XLSX、日志与总报告。前端以文件名或明确的极限模式参数识别该任务，展示固定的“极限压测 · GPU + CPU/内存（同步）”名称和模块结果表。

重试复制整个极限任务参数；不提供模块级重试。常规套件继续使用现有批次子任务展示。

## Risks / Trade-offs

- [GPU 满载与 CPU 满载可能延迟 `nvidia-smi`、SSH 日志或监控采样] → 将采样缺失作为独立监控证据，不将其静默视为低利用率；总任务继续可诊断。
- [共享 kernel/ECC/MCE/thermal 事件可同时被两个模块观察到] → 总报告标注共享主机事件及来源，保留原始模块日志，避免把重复记录解释为独立事件。
- [模块在 barrier 后异常退出] → 立即停止同伴进程组，并保留已生成的部分报告与原始日志。
- [后端重启时本地协调状态丢失] → 以远端编排进程、PID 文件和工作目录中的状态文件作为恢复依据，恢复监控而不重新下发负载。
- [新增子脚本接口影响常规运行] → 为常规独立调用保留现有默认流程，并覆盖两种入口的 Shell 合约回归。

## Migration Plan

1. 发布后保持常规压测默认模式和既有 API 行为不变。
2. 极限模式仅通过新参数和受控脚本入口创建；旧任务与历史记录不迁移。
3. 如发现编排或同步问题，隐藏极限模式入口并拒绝新建极限任务；既有常规压测不受影响。远端任务在取消时按既有进程组清理机制回收。
